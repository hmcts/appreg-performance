= AppReg Gatling performance tests

Gatling performance tests for the HMCTS Applications Register. The current smoke journey loads the Applications Register page at `https://appreg.test.apps.hmcts.net/applications-list`.

== Prerequisites

* Java 21 (JDK), available as `java` on your `PATH`
* Git
* Network access to the AppReg test environment and Maven Central/Gradle services

Gradle does not need to be installed separately: the included Gradle wrapper downloads the required version and Gatling dependencies on its first run.

== Build and run locally

From the repository root:

[source,bash]
----
./gradlew gatlingClasses
./gradlew gatlingRun -Ddebug=on
----

`-Ddebug=on` runs one virtual user and is the recommended way to validate a change. Omit it to run the configured performance profile.

Set `TEST_URL` to run the same journey against another approved environment. It must be the application origin, without the `/applications-list` path:

[source,bash]
----
TEST_URL='https://appreg.test.apps.hmcts.net' ./gradlew gatlingRun -Ddebug=on
----

Gatling writes HTML reports to `build/reports/gatling/`; the final command output includes the exact report location.

Jenkins is configured to publish Gatling reports after every CNP and nightly performance-test run, including failed runs. Each build archives `build/reports/gatling/**`, exposes a root-level `gatling-performance-reports.html` artifact alongside the Dependency-Check report, and provides a `Gatling Performance Reports` HTML link. The HTML landing pages link to the timestamped report for each simulation generated in the build; Jenkins' standard `all files in zip` download contains the complete report set.

== Test design and code structure

This project uses a modular, business-action design rather than a browser-test Page Object Model. Gatling tests the application's HTTP traffic directly, so production code is organised by reusable AppReg actions instead of pages or UI selectors.

* A scenario class exposes a focused business action as a Gatling `ChainBuilder`, for example creating an Application List, searching, or updating an Application.
* A simulation composes those actions with authentication, test data, pacing and a load profile. One-user proof simulations validate an action before it is included in a mixed workload.
* Recordings are evidence for discovering the HTTP flow; they are not test code. Extract the required requests, replace recorded values with session variables/feeders, and add relevant checks before creating a curated scenario.

This keeps common actions reusable across flows and avoids duplicating authentication, search/setup, headers and data handling. `AGENTS.md` records the same conventions for contributors using AI assistance.

== Test data progression and proof re-enablement

Every `*ProofSimulation` is retained as focused coverage for its reusable business action. A future weighted workload complements those proofs; it does not replace them.

Test-dependent proofs are enabled progressively:

. The matching Data ticket supplies one valid canonical Test data shape and its reviewed SQL.
. The scenario/proof consumes that shape using one dedicated user and allocated records.
. The one-user proof must pass against Test.
. Its proof is then re-enabled in the Jenkins Direct Gatling proof stage.

=== Wording-template reference data

Application Code and Result Code wording templates in an approved environment are reference data used by the curated journeys. Every active placeholder must use the backend-supported form `\{TYPE|REFERENCE|MAX_LENGTH}`, for example `\{TEXT|Amount of costs|10}`.

Do not use legacy `p`-delimited placeholders such as `\{TEXTpAmount of costsp10}`. They are not parsed by AppReg and cause otherwise valid Application or Result submissions to fail with HTTP 400. Verify the active `application_codes` and `resolution_codes` data before validating a wording-based proof against a new environment.

ARCPOC-1633 will subsequently scale each approved canonical SQL shape into deterministic synthetic data for the final workload. Each virtual user must receive its own allocated record set; do not use shared mutable records. This data-provisioning work is separate from the Test environment migration and from the eventual workload-profile configuration.

== Recording browser journeys

Recordings are raw browser evidence, not production-ready performance tests. They must not be added to a load profile or deployed directly. After recording, extract useful requests into the curated scenarios, replace dynamic values with session variables/feeders, define safe unique test data, and add appropriate assertions. Delete the raw recording once that assimilation is complete.

Use a dedicated, approved test account and a disposable Chrome profile. Never commit credentials, cookies, access tokens, captured personal data, or Recorder-generated response-body files.

Set the application origin and its Recorder allow-list regular expression for the approved environment. Do not include a path in `RECORDING_APP_URL`.

[source,bash]
----
export RECORDING_APP_URL='https://<approved-recording-host>'
export RECORDING_APP_URL_REGEX='https://<approved-recording-host-regex>/.*'
----

=== Persistent HTTPS certificate setup

Chrome cannot bypass a self-signed certificate for an HSTS-enabled application. Create and trust a dedicated local certificate authority (CA) for Gatling Recorder instead. Keep it in a user configuration directory so recording continues to work after a restart; never commit the private key.

[source,bash]
----
mkdir -p "$HOME/.config/gatling-recorder/staging"

openssl genrsa -out "$HOME/.config/gatling-recorder/staging/ca-key.pem" 4096

openssl req -x509 -new -sha256 -days 365 \
  -key "$HOME/.config/gatling-recorder/staging/ca-key.pem" \
  -out "$HOME/.config/gatling-recorder/staging/ca-cert.pem" \
  -subj "/CN=Gatling Recorder Staging CA" \
  -addext "basicConstraints=critical,CA:TRUE" \
  -addext "keyUsage=critical,keyCertSign,cRLSign" \
  -addext "subjectKeyIdentifier=hash"

chmod 600 "$HOME/.config/gatling-recorder/staging/ca-key.pem"

sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain \
  "$HOME/.config/gatling-recorder/staging/ca-cert.pem"
----

Fully quit Chrome after installing the CA. The `sudo` command requires macOS administrator approval because it changes the System keychain. Keep this CA only for the dedicated recording workflow. If it must be replaced, remove the existing `Gatling Recorder Staging CA` certificate from Keychain Access' *System* keychain before trusting the replacement.

The Recorder configuration is local and ignored by Git. In the Recorder UI, or in `src/gatling/resources/recorder.conf` when it exists locally, set these persistent paths:

[source,text]
----
certificatePath="/Users/<your-user>/.config/gatling-recorder/staging/ca-cert.pem"
privateKeyPath="/Users/<your-user>/.config/gatling-recorder/staging/ca-key.pem"
----

These paths are specific to the macOS user who created the CA. Every developer or build machine that runs the Recorder must create and trust its own CA, then update its local Recorder `certificatePath` and `privateKeyPath` to that user's files. Do not copy another user's private key or commit either file to the repository.

This Recorder CA is separate from the Zscaler certificate used by Java/Gradle. See <<zscaler-certificate-issue,Zscaler certificate issue>> if Gradle reports a TLS trust error.

=== HMCTS connection during recording

Follow the approved HMCTS procedure for the recording session: temporarily disconnect the relevant Zscaler Private Access/security connection, reconnect to HMCTS through F5, and then start the Recorder and disposable proxied Chrome profile. Restore the normal Zscaler/F5 connection immediately after recording.

Do not make this a permanent security bypass. Use the disposable profile only for the approved AppReg journey and do not browse unrelated sites or enter non-test credentials while the Recorder proxy is active.

=== Configure and start the Recorder

Launch Gatling Recorder from the repository root:

[source,bash]
----
./gradlew gatlingRecorder
----

Configure the Recorder as follows, then click `Start!` and confirm it switches to the recording screen with a `Stop` control:

* Mode: `HTTP Proxy`; port: `8000`.
* HTTPS mode: `Certificate Authority`.
* Certificate: `$HOME/.config/gatling-recorder/staging/ca-cert.pem`; private key: `$HOME/.config/gatling-recorder/staging/ca-key.pem`.
* Package: `recorded`; format: `Java 17`; class name: a descriptive `Recorded...` name, for example `RecordedApplicationListCreate`. Java 17 is Gatling Recorder's newest Java source template; generated code is compiled and run with this project's Java 21 toolchain.
* Enable Filters; add `$RECORDING_APP_URL_REGEX` as the only AllowList entry; leave DenyList empty.
* Keep Follow Redirects, Infer HTML resources, Automatic Referers, and Remove cache headers enabled. Leave Save & check response bodies disabled.

=== Record the browser journey

After clicking `Start!`, Gatling must show its recording screen with a `Stop` control. Only then launch the same Chrome profile through its proxy:

[source,bash]
----
open -na "Google Chrome" --args \
  --user-data-dir=/private/tmp/gatling-recording-chrome \
  --proxy-server=http://127.0.0.1:8000
----

Open `$RECORDING_APP_URL` in that proxied Chrome window and sign in using the approved test account. Complete any setup that does not need recording because it is already covered by the repository, such as login or creating a list. Once the intended start page is ready, use Gatling's `Clear` button to remove that setup traffic. Confirm the Recorder remains on its recording screen, then complete only the minimum target journey.

When finished, click `Stop`, review the request list, and save the recording. The generated Java source is written under `src/gatling/java/recorded/`.

== Zscaler certificate issue

If the Gradle wrapper fails while downloading Gradle or dependencies with a `PKIX path building failed` or `certificate_unknown` error, Java does not trust the Zscaler TLS-inspection certificate.

Download the current Zscaler certificates from https://git.cgi.com/sam.franklin/wsl-zscalar-config, then add the root certificate to a Java trust store used by Gradle. Do not disable TLS validation.

For example, create a dedicated local trust store from the downloaded PEM certificate:

[source,bash]
----
keytool -importcert -noprompt \
  -alias zscaler-root-ca \
  -file /path/to/ZscalerRootCertificate.pem \
  -keystore "$HOME/.gradle/zscaler-truststore.p12" \
  -storetype PKCS12 \
  -storepass changeit

export GRADLE_OPTS="-Djavax.net.ssl.trustStore=$HOME/.gradle/zscaler-truststore.p12 -Djavax.net.ssl.trustStoreType=PKCS12 -Djavax.net.ssl.trustStorePassword=changeit"
./gradlew gatlingClasses
----

*Use the certificate file name supplied by the download. The trust store is local-only and should not be committed.*

== Authentication

The default `-DauthMode=none` runs the unauthenticated application-load journey.

=== Production-like SSO UI journey

`-DauthMode=sso-login` runs AppReg's real HTTP SSO sequence for each virtual user: `/sso/login`, Entra authorisation, credential submission, Entra's KMSI continuation, then AppReg's SSO callback and `/sso/me`. Gatling follows the Entra redirects and keeps the resulting `appreg.sid` cookie in that virtual user's cookie jar while it performs the UI journey. This does not require an AppReg product change.

The run requires these masked runtime variables:

* `TEST_USER_EMAIL` — one dedicated account for the one-user proof, or an account-name template containing `{index}` for multi-user runs. `APPREG_TEST_ACCOUNT_TEMPLATE` is an optional alias.
* `TEST_USERS_PASSWORD` — the shared password for dedicated test accounts. `APPREG_TEST_USER_PASSWORD` is an optional alias.
* `TENANT_ID` — the Entra tenant. `APPREG_TENANT_ID` is an optional alias.

The shared password is never put in a feeder, log, report, or file.

For the initial Test/performance-environment proof, Jenkins uses the approved static account `appreg-001@dev.platform.hmcts.net` and retrieves only its shared password and tenant ID from Test Key Vault. The later multi-user profile will derive its allocated accounts from the agreed `appreg-<three-digit-index>@dev.platform.hmcts.net` pattern rather than store 500 individual email secrets.

SSO login is deliberately included in the measured traffic. AppReg currently rate-limits `/sso/login` to ten requests per minute, so start with one user and retain a login rate below that limit. Do not repeatedly log in inside a journey loop. The first Test/performance-environment run must be a one-user proof because Entra response shapes can change.

The curated load profile defaults to one SSO user through `PERFORMANCE_TEST_USERS=1`. Increase that only after supplying `APPREG_TEST_ACCOUNT_TEMPLATE`, confirming enough dedicated accounts, and agreeing the Entra/AppReg login rate. `AUTH_MODE=sso-login` is set by the Jenkins file; local runs can set `-DauthMode=sso-login` instead.

The CNP push pipeline currently runs the curated `AppRegSimulation` and the non-destructive one-user `ActivityAuditReportProofSimulation` against Test. All other `*ProofSimulation` classes remain available for local validation. They will be re-enabled in CNP individually once their matching Data ticket has supplied the required Test reference/seed data and the one-user proof passes. The update proof composes the reusable search action, so the search proof remains available for local validation but is not run separately in CNP. The create, update, add, result, bulk-officials, bulk-fee, upload and close proofs change persistent test data, so they must retain their dedicated account and test-data controls.

After the landing page HTML and main JavaScript load, the UI performs `GET /application-lists?pageNumber=0&pageSize=1`. The request is same-origin and authenticated by the AppReg session cookie; it verifies that the signed-in user can retrieve the protected applications-list data.

== Application List create proof

`ApplicationListCreateScenario` is a reusable authenticated chain that loads the Application Lists page, extracts the anti-forgery token, creates a list with a unique description, and retrieves the created list. It is consumed by `ApplicationListCreateProofSimulation`, a dedicated single-user validation simulation.

The proof creates persistent test data. Run it only against an approved environment with a dedicated test account, and remove or otherwise manage the created list according to the environment's test-data policy.

To run the one-user proof, set `TEST_URL` to the approved origin and supply the SSO variables described above:

[source,bash]
----
TEST_URL="$RECORDING_APP_URL" \
  ./gradlew gatlingRun \
  --simulation simulations.ApplicationListCreateProofSimulation
----

The recorded court-location code is the default. Override it with an approved code when required:

[source,bash]
----
TEST_URL="$RECORDING_APP_URL" \
  ./gradlew gatlingRun \
  -DappRegCourtLocationCode=<approved-court-location-code> \
  --simulation simulations.ApplicationListCreateProofSimulation
----

== Application update proof

`UpdateApplicationScenario` is a reusable authenticated chain for ARCPOC-1615. It updates the Application List and Application identifiers held in the Gatling session, retrieving the relevant entry and application-code metadata before submitting the update and verifying a successful response. It is consumed by `UpdateApplicationProofSimulation`.

This proof is destructive. It validates the reusable `Bulk` search action, then creates an isolated Application List and Application before updating that known entry with new disposable values. It must not be run against production or records containing real personal data. Before a multi-user workload is introduced, agree deterministic allocation and cleanup for the created data.

To run the one-user proof, supply the SSO values described above:

[source,bash]
----
TEST_URL="$RECORDING_APP_URL" \
  ./gradlew gatlingRun \
  --simulation simulations.UpdateApplicationProofSimulation
----

The proof reads the application code from its created entry. It uses the shared search action, which defaults to searching for `Bulk`; override the search description when the approved POC data requires it:

[source,bash]
----
-DappRegApplicationListSearchDescription=<approved-list-description>
----

== Activity Audit report proof

`ActivityAuditReportScenario` is the reusable, non-destructive reporting action for ARCPOC-1599. It submits an Activity Audit report job, polls it until AppReg reports `SUCCEEDED` or `COMPLETED`, then downloads the generated CSV. The downloaded response body is not written to the repository or Gatling report.

`ActivityAuditReportProofSimulation` authenticates one approved user and runs that action. It needs no synthetic test data. By default it requests `ADD_APPLICATION` activity from the previous UTC day through today; override the criteria for an approved environment when required:

No report-generation response-time or throughput NFR has been agreed for AppReg. This proof is therefore a functional benchmark and a starting point for controlled limit exploration, not evidence that a performance requirement has been met. Record its timings and report size as findings; add workload profiles and pass/fail thresholds only after the reporting requirements are agreed.

[source,bash]
----
TEST_URL="$RECORDING_APP_URL" \
  ./gradlew gatlingRun \
  --simulation simulations.ActivityAuditReportProofSimulation
----

[source,bash]
----
-DappRegActivityAuditReportDateFrom=<YYYY-MM-DD> \
-DappRegActivityAuditReportDateTo=<YYYY-MM-DD> \
-DappRegActivityAuditReportActivity=<approved-activity-type>
----

== Application List update and close proof

ARCPOC-1620 has two separate reusable actions: `UpdateApplicationListScenario` updates an open Application List, and `CloseApplicationListScenario` closes a list that already satisfies AppReg's closure rules. They remain separate because the eventual workload uses a 90% simple-update and 10% close split within the ticket's overall allocation.

`UpdateAndCloseApplicationListProofSimulation` creates proof-only close-ready data: one isolated list, one completed Application, a paid fee, respondent, Magistrate official and `AUTH` result. The simple update action changes the list date, time, description and duration before the close action runs; it retains the existing court/location unless an approved replacement code is supplied. This proof is destructive and permanently closes its created list. Final workload simulations will instead use separate allocated open-list and close-ready-list seed data.

To run the one-user proof:

[source,bash]
----
TEST_URL="$RECORDING_APP_URL" \
  ./gradlew gatlingRun \
  --simulation simulations.UpdateAndCloseApplicationListProofSimulation
----

The duration used by both actions defaults to ten hours and can be overridden for an approved environment:

[source,bash]
----
-DappRegApplicationListDurationHours=<positive-hours>
----

== Useful options

* `-Ddebug=on` — run a single virtual user.
* `-Denv=<name>` — override the configured environment label.
* `-DauthMode=none` — run without authentication (default).
* `-DauthMode=sso-login` — execute the real AppReg/Entra HTTP login before the UI journey.
