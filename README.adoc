= AppReg Gatling performance tests

Gatling performance tests for the HMCTS Applications Register. The current smoke journey loads the Applications Register page at `https://appreg.test.apps.hmcts.net/applications-list`.

== Prerequisites

* Java 21 (JDK), available as `java` on your `PATH`
* Git
* Network access to the AppReg test environment and Maven Central/Gradle services

Gradle does not need to be installed separately: the included Gradle wrapper downloads the required version and Gatling dependencies on its first run.

== Build and run locally

From the repository root:

[source,bash]
----
./gradlew gatlingClasses
./gradlew gatlingRun -Ddebug=on
----

`-Ddebug=on` runs one virtual user and is the recommended way to validate a change. Omit it to run the configured performance profile.

Set `TEST_URL` to run the same journey against another approved environment. It must be the application origin, without the `/applications-list` path:

[source,bash]
----
TEST_URL='https://appreg.test.apps.hmcts.net' ./gradlew gatlingRun -Ddebug=on
----

Gatling writes HTML reports to `build/reports/gatling/`; the final command output includes the exact report location.

Jenkins is configured to publish Gatling reports after every CNP and nightly performance-test run, including failed runs. Each build archives `build/reports/gatling/**`, exposes a root-level `gatling-performance-reports.html` artifact alongside the Dependency-Check report, and provides a `Gatling Performance Reports` HTML link. The HTML landing pages link to the timestamped report for each simulation generated in the build; Jenkins' standard `all files in zip` download contains the complete report set.

For failed `GET /application-lists/{uuid}` calls, the Jenkins console additionally writes a sanitised correlation line containing only the business action, request name, HTTP status and Application List UUID. It never logs response bodies, cookies or credentials. Search the console log for `Application List GET failure` and use the UUID to correlate with Insight.

== Test design and code structure

This project uses a modular, business-action design rather than a browser-test Page Object Model. Gatling tests the application's HTTP traffic directly, so production code is organised by reusable AppReg actions instead of pages or UI selectors.

* A scenario class exposes a focused business action as a Gatling `ChainBuilder`, for example creating an Application List, searching, or updating an Application.
* A simulation composes those actions with authentication, test data, pacing and a load profile. One-user proof simulations validate an action before it is included in a mixed workload.
* Recordings are evidence for discovering the HTTP flow; they are not test code. Extract the required requests, replace recorded values with session variables/feeders, and add relevant checks before creating a curated scenario.

This keeps common actions reusable across flows and avoids duplicating authentication, search/setup, headers and data handling. `AGENTS.md` records the same conventions for contributors using AI assistance.

== Test data progression and proof re-enablement

Every `*ProofSimulation` is retained as focused coverage for its reusable business action. A future weighted workload complements those proofs; it does not replace them.

Test-dependent proofs are enabled progressively:

. The matching Data ticket supplies one valid canonical Test data shape and its reviewed SQL.
. The scenario/proof consumes that shape using one dedicated user and allocated records.
. The one-user proof must pass against Test.
. Its proof is then re-enabled in the Jenkins Direct Gatling proof stage.

=== Wording-template reference data

Application Code and Result Code wording templates in an approved environment are reference data used by the curated journeys. Every active placeholder must use the backend-supported form `\{TYPE|REFERENCE|MAX_LENGTH}`, for example `\{TEXT|Amount of costs|10}`.

Do not use legacy `p`-delimited placeholders such as `\{TEXTpAmount of costsp10}`. They are not parsed by AppReg and cause otherwise valid Application or Result submissions to fail with HTTP 400. Verify the active `application_codes` and `resolution_codes` data before validating a wording-based proof against a new environment.

=== ARCPOC-1633 baseline and ARCPOC-1706 deterministic allocation

The first ARCPOC-1633 validation is the existing seeded Jenkins batch: it runs every enabled proof after one canonical seed execution. This establishes that all canonical shapes coexist and that each proof changes only its own allocation. In the simplified pipeline this is `RUN_MODE=framework-proof`, normally with `RESET_DATABASE=false`; use a reset only when a clean masked-database baseline is required.

ARCPOC-1706 scales the approved shapes into deterministic synthetic data for the agreed workload. It:

* retains the canonical SQL as the readable source shape for each business action;
* generates sufficient non-overlapping list and entry allocations for the requested users and journey mix;
* builds an exact, deterministic action plan from the reviewed action totals;
* passes only the exact plan rows to queue feeders, without committing generated identifiers or personal data;
* assigns one mutable record set to one virtual-user action; and
* runs reset, seed/allocation and Gatling in the documented pipeline order.

The allocation controls are per action, not one shared count. `data/seed/selective-application-list-shapes.psql` creates the requested action shape in one database session and returns its feeder rows. This avoids producing unrelated destructive records merely because one action has a larger allocation, and avoids a database connection per allocated row.

`data/seed/workload/allocation-profile.properties` is the version-controlled source of the agreed smoke, validation and performance-workload volumes. The performance plan has exactly 35,000 actions: 500 users × 70 actions each. It contains 31,584 destructive feeder-backed actions, 2,517 runtime Create Application List actions and 899 stable non-destructive Other UI Operations. The seed capacity contains 37,904 destructive rows—a 20% reserve per destructive action, rounded up—but the workload feeder receives only the exact scheduled rows. This preserves a deterministic execution mix without record reuse.

=== Deterministic feeder-backed workload

`AppRegWorkloadSimulation` is the bounded multi-user benchmark simulation. Each virtual user logs in once using a distinct `appreg-{index}@dev.platform.hmcts.net` account. A deterministic largest-deficit plan evenly interleaves the reviewed action totals and assigns a fixed action sequence to each account. Destructive actions use Gatling queue feeders, so each allocated list/entry set is consumed once and is never shared between virtual users.

The workload currently represents the 2.57% Other UI Operations allocation with the non-destructive Application List search action. Activity Audit reporting remains a separate functional benchmark until a reporting workload expectation is agreed.

The workload paces actions to one completed action per virtual user per minute. It has no response-time pass/fail threshold: its report establishes and compares benchmarks. It does fail for any functional HTTP error; this keeps platform and application failures visible rather than masking them behind an arbitrary error allowance.

Use Jenkins **Build with Parameters** with one of these combinations:

* `RUN_MODE=application-diagnostic`, `MAX_USERS=100`, `RUN_DURATION_MINUTES=5`, `RESET_DATABASE=false` for a short destructive diagnostic run. `MAX_USERS` may be increased up to 500 when needed, provided the requested users and minutes stay within the `35000`-action envelope.
* `RUN_MODE=framework-proof`, `RESET_DATABASE=false` for the full one-user proof suite after a fresh seed.
* `RUN_MODE=performance`, `RESET_DATABASE=false` for the full formal run. This mode always performs the read-only 500-account preflight first, then seeds fresh data and runs the fixed 500-user, 70-minute workload.

The diagnostic mode uses the reviewed `performance` action mix but scales it to a bounded run of the requested size. The full `performance` mode keeps the agreed 500-user, 70-minute weighted workload. It starts its 500 accounts across 500 seconds (one login per second), based on the read-only preflight evidence. Its final user should complete after approximately 78 minutes and 20 seconds, leaving nearly twelve minutes of the configured 90-minute Jenkins stage timeout for setup and report generation.

Before a full diagnostic or formal workload run, pause development activity that could change the measured system: AppReg deployments, database schema or reference-data changes, seed-SQL changes, and workload-profile/code changes. Record the Git commit, selected Jenkins parameters and Test-environment version before starting. Resume those changes only after the run has finished and its reports have been retained; otherwise the result is not a reproducible benchmark. This is an operational coordination requirement, not a Jenkins-enforced deployment freeze.

This data-provisioning work is separate from Test-environment migration and from workload-profile configuration. A weighted workload must not be enabled until the data allocation and final profile have both been reviewed.

== Recording browser journeys

Recordings are raw browser evidence, not production-ready performance tests. They must not be added to a load profile or deployed directly. After recording, extract useful requests into the curated scenarios, replace dynamic values with session variables/feeders, define safe unique test data, and add appropriate assertions. Delete the raw recording once that assimilation is complete.

Use a dedicated, approved test account and a disposable Chrome profile. Never commit credentials, cookies, access tokens, captured personal data, or Recorder-generated response-body files.

Set the application origin and its Recorder allow-list regular expression for the approved environment. Do not include a path in `RECORDING_APP_URL`.

[source,bash]
----
export RECORDING_APP_URL='https://<approved-recording-host>'
export RECORDING_APP_URL_REGEX='https://<approved-recording-host-regex>/.*'
----

=== Persistent HTTPS certificate setup

Chrome cannot bypass a self-signed certificate for an HSTS-enabled application. Create and trust a dedicated local certificate authority (CA) for Gatling Recorder instead. Keep it in a user configuration directory so recording continues to work after a restart; never commit the private key.

[source,bash]
----
mkdir -p "$HOME/.config/gatling-recorder/staging"

openssl genrsa -out "$HOME/.config/gatling-recorder/staging/ca-key.pem" 4096

openssl req -x509 -new -sha256 -days 365 \
  -key "$HOME/.config/gatling-recorder/staging/ca-key.pem" \
  -out "$HOME/.config/gatling-recorder/staging/ca-cert.pem" \
  -subj "/CN=Gatling Recorder Staging CA" \
  -addext "basicConstraints=critical,CA:TRUE" \
  -addext "keyUsage=critical,keyCertSign,cRLSign" \
  -addext "subjectKeyIdentifier=hash"

chmod 600 "$HOME/.config/gatling-recorder/staging/ca-key.pem"

sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain \
  "$HOME/.config/gatling-recorder/staging/ca-cert.pem"
----

Fully quit Chrome after installing the CA. The `sudo` command requires macOS administrator approval because it changes the System keychain. Keep this CA only for the dedicated recording workflow. If it must be replaced, remove the existing `Gatling Recorder Staging CA` certificate from Keychain Access' *System* keychain before trusting the replacement.

The Recorder configuration is local and ignored by Git. In the Recorder UI, or in `src/gatling/resources/recorder.conf` when it exists locally, set these persistent paths:

[source,text]
----
certificatePath="/Users/<your-user>/.config/gatling-recorder/staging/ca-cert.pem"
privateKeyPath="/Users/<your-user>/.config/gatling-recorder/staging/ca-key.pem"
----

These paths are specific to the macOS user who created the CA. Every developer or build machine that runs the Recorder must create and trust its own CA, then update its local Recorder `certificatePath` and `privateKeyPath` to that user's files. Do not copy another user's private key or commit either file to the repository.

This Recorder CA is separate from the Zscaler certificate used by Java/Gradle. See <<zscaler-certificate-issue,Zscaler certificate issue>> if Gradle reports a TLS trust error.

=== HMCTS connection during recording

Follow the approved HMCTS procedure for the recording session: temporarily disconnect the relevant Zscaler Private Access/security connection, reconnect to HMCTS through F5, and then start the Recorder and disposable proxied Chrome profile. Restore the normal Zscaler/F5 connection immediately after recording.

Do not make this a permanent security bypass. Use the disposable profile only for the approved AppReg journey and do not browse unrelated sites or enter non-test credentials while the Recorder proxy is active.

=== Configure and start the Recorder

Launch Gatling Recorder from the repository root:

[source,bash]
----
./gradlew gatlingRecorder
----

Configure the Recorder as follows, then click `Start!` and confirm it switches to the recording screen with a `Stop` control:

* Mode: `HTTP Proxy`; port: `8000`.
* HTTPS mode: `Certificate Authority`.
* Certificate: `$HOME/.config/gatling-recorder/staging/ca-cert.pem`; private key: `$HOME/.config/gatling-recorder/staging/ca-key.pem`.
* Package: `recorded`; format: `Java 17`; class name: a descriptive `Recorded...` name, for example `RecordedApplicationListCreate`. Java 17 is Gatling Recorder's newest Java source template; generated code is compiled and run with this project's Java 21 toolchain.
* Enable Filters; add `$RECORDING_APP_URL_REGEX` as the only AllowList entry; leave DenyList empty.
* Keep Follow Redirects, Infer HTML resources, Automatic Referers, and Remove cache headers enabled. Leave Save & check response bodies disabled.

=== Record the browser journey

After clicking `Start!`, Gatling must show its recording screen with a `Stop` control. Only then launch the same Chrome profile through its proxy:

[source,bash]
----
open -na "Google Chrome" --args \

Open `$RECORDING_APP_URL` in that proxied Chrome window and sign in using the approved test account. == Zscaler certificate issue

If the Gradle wrapper fails while downloading Gradle or dependencies with a `PKIX path building failed` or `certificate_unknown` error, Java does not trust the Zscaler TLS-inspection certificate.

Download the current Zscaler certificates from https://git.cgi.com/sam.franklin/wsl-zscalar-config, then add the root certificate to a Java trust store used by Gradle. Do not disable TLS validation.

For example, create a dedicated local trust store from the downloaded PEM certificate:

[source,bash]
----
keytool -importcert -noprompt \
  -alias zscaler-root-ca \
  -file /path/to/ZscalerRootCertificate.pem \
  -keystore "$HOME/.gradle/zscaler-truststore.p12" \
  -storetype PKCS12 \
  -storepass changeit

export GRADLE_OPTS="-Djavax.net.ssl.trustStore=$HOME/.gradle/zscaler-truststore.p12 -Djavax.net.ssl.trustStoreType=PKCS12 -Djavax.net.ssl.trustStorePassword=changeit"
./gradlew gatlingClasses
----

*Use the certificate file name supplied by the download. The trust store is local-only and should not be committed.*

== Authentication

The default `-DauthMode=none` runs the unauthenticated application-load journey.

=== Production-like SSO UI journey

`-DauthMode=sso-login` runs AppReg's real HTTP SSO sequence for each virtual user: `/sso/login`, Entra authorisation, credential submission, Entra's KMSI continuation, then AppReg's SSO callback and `/sso/me`. Gatling follows the Entra redirects and keeps the resulting `appreg.sid` cookie in that virtual user's cookie jar while it performs the UI journey. This does not require an AppReg product change.

The run requires these masked runtime variables:

* `TEST_USER_EMAIL` — one dedicated account for the one-user proof, or an account-name template containing `{index}` for multi-user runs. `{index}` is always zero-padded to three digits: `appreg-{index}@dev.platform.hmcts.net` produces `appreg-001@dev.platform.hmcts.net`, `appreg-010@dev.platform.hmcts.net` and so on. `APPREG_TEST_ACCOUNT_TEMPLATE` is an optional alias.
* `TEST_USERS_PASSWORD` — the shared password for dedicated test accounts. `APPREG_TEST_USER_PASSWORD` is an optional alias.
* `TENANT_ID` — the Entra tenant. `APPREG_TENANT_ID` is an optional alias.

The shared password is never put in a feeder, log, report, or file.

Jenkins uses the approved static account `appreg-001@dev.platform.hmcts.net` for one-user proofs and retrieves only its shared password and tenant ID from Test Key Vault. The feeder-backed multi-user workload derives its 500 allocated accounts from the agreed `appreg-<three-digit-index>@dev.platform.hmcts.net` pattern rather than store 500 individual email secrets.

All curated Gatling traffic now sends the shared `User-Agent` value `Gatling Performance Runner` by default. Override it with `-DappRegUserAgent=<value>` or `APPREG_USER_AGENT=<value>` when you need to mark a specific run clearly in environment, ingress, or Application Insights logs.

SSO login is deliberately included in the measured traffic. The platform allowance is ten login requests per second, but the Test workload and its read-only preflight deliberately use one login per second following observed Test-environment failures at a higher controlled rate. Do not repeatedly log in inside a journey loop. The preflight is a controlled readiness gate for the application workload, not an SSO performance test: it hardens the ramp against isolated transient authentication failures without masking persistent failures. If an initial preflight account fails, Jenkins places its dedicated account identifier in the workspace-only `build/login-preflight-retry.csv` queue and retries it once after the initial 500-account ramp has finished, again at one login per second. The performance gate passes only if that trailing retry is clean; passwords are never written to the queue. A green 500-account preflight is required before a destructive performance workload run.

The curated load profile defaults to one SSO user through `PERFORMANCE_TEST_USERS=1`. Increase that only after supplying `APPREG_TEST_ACCOUNT_TEMPLATE` and confirming enough dedicated accounts. `AUTH_MODE=sso-login` is set by the Jenkins file; local runs can set `-DauthMode=sso-login` instead.

=== Run profiles and configuration

The current modes are intentionally conservative:

* `-Ddebug=on` is a local smoke mode: one virtual user with pauses disabled.
* `TEST_TYPE=pipeline` is the Jenkins proof mode: the configured `PERFORMANCE_TEST_USERS` count, currently one, with SSO enabled by Jenkins.
* `TEST_TYPE=perftest` is reserved for an agreed workload run. Do not use it for a final workload until ARCPOC-1633 has provisioned allocated data and the selected workload profile has been reviewed.

Set the target once with `-DappRegConcurrentUsers=<count>`; it defaults to `PERFORMANCE_TEST_USERS` (one in Jenkins). The legacy one-pass framework derives its SSO arrival ramp from the platform allowance of ten login requests per second. `appRegSuccessfulRequestsThreshold=95` remains separately configurable for that legacy warm-up simulation only. `AppRegWorkloadSimulation` instead reads its user count, duration, login ramp and allocations from the derived workload profile selected by Jenkins `RUN_MODE`, or from `-DappRegWorkloadProfile` for direct local execution.

The legacy `AppRegSimulation` is a one-pass framework/warm-up journey: each virtual user logs in, performs its journey, then exits. The bounded `AppRegWorkloadSimulation` is the current 500-account workload implementation: each user logs in once, executes its fixed deterministic action sequence at one action per minute, and exits. It uses an open injection because the finite run has exactly 500 allocated accounts and must not replace completed users or reuse their accounts/data. A future sustained-concurrency profile requires an explicit account/data allocation design and must be introduced separately.

Do not override workload rates, durations or success thresholds without an agreed NFR and enough independently allocated accounts and records. Invalid values fail fast when Gatling starts.

The CNP push pipeline runs `AppRegSimulation`, the non-destructive one-user `ActivityAuditReportProofSimulation`, and every proof with an approved canonical seed allocation against Test. The update proof composes the reusable search action, so the search proof remains available for local validation but is not run separately in CNP. Destructive create, update, add, result, bulk, upload and close proofs retain their dedicated account and data-allocation controls.

After the landing page HTML and main JavaScript load, the UI performs `GET /application-lists?pageNumber=0&pageSize=1`. The request is same-origin and authenticated by the AppReg session cookie; it verifies that the signed-in user can retrieve the protected applications-list data.

== Application List create proof

`ApplicationListCreateScenario` is a reusable authenticated chain that loads the Application Lists page, extracts the anti-forgery token, creates a list with a unique description, and retrieves the created list. It is consumed by `ApplicationListCreateProofSimulation`, a dedicated single-user validation simulation.

The proof creates persistent test data. Run it only against an approved environment with a dedicated test account, and remove or otherwise manage the created list according to the environment's test-data policy.

To run the one-user proof, set `TEST_URL` to the approved origin and supply the SSO variables described above:

== Application update proof

`UpdateApplicationScenario` is a reusable authenticated chain for ARCPOC-1615. It updates the Application List and Application identifiers held in the Gatling session, retrieving the relevant entry and application-code metadata before submitting the update and verifying a successful response. It is consumed by `UpdateApplicationProofSimulation`.

This proof is destructive. It updates the canonical seeded editable Application List and Application, using new disposable values. It must not be run against production or records containing real personal data. It requires the `APPREG_SEED_EDITABLE_LIST_ID` and `APPREG_SEED_EDITABLE_ENTRY_ID` UUIDs emitted by `data/seed/canonical-application-list-shapes.psql` (or written to `build/seed-allocation.env` by the Jenkins seed stage).

To run the one-user proof, supply the SSO values described above:

[source,bash]
----
APPREG_SEED_EDITABLE_LIST_ID=<seeded-list-uuid> \
APPREG_SEED_EDITABLE_ENTRY_ID=<seeded-entry-uuid> \
TEST_URL="$RECORDING_APP_URL" \
  ./gradlew gatlingRun \
  --simulation simulations.UpdateApplicationProofSimulation
----

The proof reads the application code from its allocated entry before submitting the update. The data reset/seed process must run again before repeating a destructive proof against the same allocation.

== Application add proof

`AddApplicationScenario` is a reusable authenticated chain for ARCPOC-1616. It assumes the caller has set `applicationListId`, searches for the selected application code, adds an Application, retrieves the resulting entry data, and completes the Application.

It requires `APPREG_SEED_ADD_APPLICATION_LIST_ID`, emitted by `data/seed/canonical-application-list-shapes.psql` or the Jenkins seed stage. Run it only against an approved environment with a dedicated account; do not include it in a multi-user workload until test-data allocation and cleanup are agreed.

APPREG_SEED_ADD_APPLICATION_LIST_ID=<seeded-list-uuid> \

== Activity Audit report proof

`ActivityAuditReportScenario` is the reusable, non-destructive reporting action for ARCPOC-1599. It submits an Activity Audit report job, polls it until AppReg reports `SUCCEEDED` or `COMPLETED`, then downloads the generated CSV. The downloaded response body is not written to the repository or Gatling report.

`ActivityAuditReportProofSimulation` authenticates one approved user and runs that action. It needs no synthetic test data. By default it requests `ADD_APPLICATION` activity from the previous UTC day through today; override the criteria for an approved environment when required:

No report-generation response-time or throughput NFR has been agreed for AppReg. This proof is therefore a functional benchmark and a starting point for controlled limit exploration, not evidence that a performance requirement has been met. Record its timings and report size as findings; add workload profiles and pass/fail thresholds only after the reporting requirements are agreed.

== Application List update and close proof

ARCPOC-1620 has two separate reusable actions: `UpdateApplicationListScenario` updates an open Application List, and `CloseApplicationListScenario` closes a list that already satisfies AppReg's closure rules. They remain separate because the eventual workload uses a 90% simple-update and 10% close split within the ticket's overall allocation.

`UpdateApplicationListProofSimulation` validates the simple-update action against an allocated ordinary open list. It requires `APPREG_SEED_UPDATE_LIST_ID` and must not use close-ready data; a simple update and a close action must never share a mutable list allocation.

[source,bash]
----
APPREG_SEED_UPDATE_LIST_ID=<allocated-open-list-id> \
TEST_URL='https://appreg.test.apps.hmcts.net' \
  ./gradlew gatlingRun \
  --simulation simulations.UpdateApplicationListProofSimulation
----

`UpdateAndCloseApplicationListProofSimulation` consumes one allocated close-ready Application List and entry. The seed must contain a completed Application, a paid fee, respondent, official, Result and positive duration. The proof first verifies that the allocated entry can be retrieved, then updates the list date, time, description and duration before closing the list. It is destructive and permanently closes its allocated list; rerun the seed process or allocate a new record before every execution.

To run the one-user proof:

[source,bash]
----
APPREG_SEED_CLOSE_READY_LIST_ID=<allocated-list-id> \
APPREG_SEED_CLOSE_READY_ENTRY_ID=<allocated-entry-id> \
TEST_URL='https://appreg.test.apps.hmcts.net' \
  ./gradlew gatlingRun \
  --simulation simulations.UpdateAndCloseApplicationListProofSimulation
----

The update values default to a ten-hour, eleven-minute duration, time `11:01`, description `Gatling application list update proof`, and the current list's court/location. Override only for an approved environment:

[source,bash]
----
-DappRegApplicationListDurationHours=<positive-hours> \
-DappRegApplicationListDurationMinutes=<non-negative-minutes> \
-DappRegApplicationListUpdateTime=<HH:MM> \
-DappRegApplicationListUpdateDescription=<safe-disposable-description> \
-DappRegUpdatedCourtLocationCode=<approved-court-location-code>
----
