= AppReg Gatling performance tests

Gatling performance tests for the HMCTS Applications Register. The current smoke journey loads the Applications Register page at `https://appreg.test.apps.hmcts.net/applications-list`.

== Prerequisites

* Java 21 (JDK), available as `java` on your `PATH`
* Git
* Network access to the AppReg test environment and Maven Central/Gradle services

Gradle does not need to be installed separately: the included Gradle wrapper downloads the required version and Gatling dependencies on its first run.

== Build and run locally

From the repository root:

[source,bash]
----
./gradlew gatlingClasses
./gradlew gatlingRun -Ddebug=on
----

`-Ddebug=on` runs one virtual user and is the recommended way to validate a change. Omit it to run the configured performance profile.

Set `TEST_URL` to run the same journey against another approved environment. It must be the application origin, without the `/applications-list` path:

[source,bash]
----
TEST_URL='https://appreg.test.apps.hmcts.net' ./gradlew gatlingRun -Ddebug=on
----

Gatling writes HTML reports to `build/reports/gatling/`; the final command output includes the exact report location.

== Zscaler certificate issue

If the Gradle wrapper fails while downloading Gradle or dependencies with a `PKIX path building failed` or `certificate_unknown` error, Java does not trust the Zscaler TLS-inspection certificate.

Download the current Zscaler certificates from https://git.cgi.com/sam.franklin/wsl-zscalar-config, then add the root certificate to a Java trust store used by Gradle. Do not disable TLS validation.

For example, create a dedicated local trust store from the downloaded PEM certificate:

[source,bash]
----
keytool -importcert -noprompt \
  -alias zscaler-root-ca \
  -file /path/to/ZscalerRootCertificate.pem \
  -keystore "$HOME/.gradle/zscaler-truststore.p12" \
  -storetype PKCS12 \
  -storepass changeit

export GRADLE_OPTS="-Djavax.net.ssl.trustStore=$HOME/.gradle/zscaler-truststore.p12 -Djavax.net.ssl.trustStoreType=PKCS12 -Djavax.net.ssl.trustStorePassword=changeit"
./gradlew gatlingClasses
----

*Use the certificate file name supplied by the download. The trust store is local-only and should not be committed.*

== Authentication

The default `-DauthMode=none` runs the unauthenticated application-load journey.

For scale tests, acquire a short-lived application access token before starting Gatling and pass it through a masked runtime variable:

[source,bash]
----
APPREG_ACCESS_TOKEN='token supplied by the pipeline' \
  ./gradlew gatlingRun -Ddebug=on -DauthMode=client-credentials
----

For a local proof of concept, use the same pattern with a short-lived token for a dedicated test identity. Do not provide a user password, Key Vault credential, or client secret to Gatling.

Authenticated runs against Cypress-supported demo or staging targets automatically use their paired AppReg API host. For any other target, set `APPREG_API_BASE_URL` explicitly to the API origin. Gatling calls the protected, read-only `GET /application-lists` endpoint after the UI shell request and expects a `200` JSON response.

In Jenkins, the runner should use its workload identity to retrieve the OAuth client credential from Key Vault, request the token once, and expose only the short-lived token to Gatling. Do not commit credentials, add them to feeders, or use personal Microsoft accounts.

Until the token endpoint is confirmed, it remains runtime configuration. To validate the client-credentials wiring directly, set all of the following variables before running with `-DauthMode=client-credentials`:

* `APPREG_TOKEN_ENDPOINT`
* `APPREG_CLIENT_ID`
* `APPREG_CLIENT_SECRET`
* `APPREG_TOKEN_SCOPE`

This fallback obtains a token per virtual user, so it is intended only for wiring validation—not a scale test.

For the temporary local proof of concept, `-DauthMode=password-grant` supports the same dedicated non-production test identity pattern used by the frontend API tests. It accepts `APPREG_TOKEN_ENDPOINT` as an endpoint override; otherwise it builds the Microsoft Entra endpoint from `TENANT_ID`. The required client, scope, and test-user values can use either the `APPREG_`-prefixed names or the Jenkins-compatible names (`TENANT_ID`, `CLIENT_ID`, `CLIENT_SECRET`, `SCOPE`, `TEST_USER_EMAIL`, and `TEST_USERS_PASSWORD`).

Password grant is for this one-user POC only. Prefer `APPREG_ACCESS_TOKEN` when available, and do not use password grant for a scaled test.

=== Token-pool bootstrap for a pipeline run

`-DauthMode=token-pool` acquires a short-lived token for each dedicated performance-test account before Gatling begins the AppReg journey. Jenkins supplies the endpoint, client values, account password and account-name template from Key Vault as masked environment variables. Gatling receives only the resulting tokens in memory.

The required variables are:

* `TEST_USER_EMAIL` — account-name template containing `{index}`, for example `appreg-perf-{index}@example.test`. It is runtime configuration so the actual naming convention can be changed without code changes. `APPREG_TEST_ACCOUNT_TEMPLATE` remains an optional AppReg-specific alias.
* `TEST_USERS_PASSWORD` — the shared password for the dedicated test accounts. `APPREG_TEST_USER_PASSWORD` remains an optional alias.
* `TENANT_ID`, `CLIENT_ID`, `CLIENT_SECRET`, and `SCOPE`. The `APPREG_`-prefixed equivalents remain optional aliases.

The profile calculates its account count: one for debug, `numberOfPipelineUsers` for the pipeline profile, and the expected number of users created by the perftest injection profile. Override the reservation explicitly with `-DaccountCount=<number>` when needed.

Requests are serial, with a one-second default interval, retry only transient `429`/`5xx` responses, and honour a numeric `Retry-After` response. Configure `APPREG_TOKEN_REQUEST_INTERVAL_MILLIS` (default `1000`) and `APPREG_TOKEN_MAX_RETRIES` (default `3`) only when Entra capacity has been agreed.

The utility records only the next account index in `build/appreg-token-pool.next-index`; it never writes tokens, passwords, client secrets, or Entra responses. Set `APPREG_ACCOUNT_CURSOR_FILE` to a retained Jenkins workspace path for consecutive batches, or set `APPREG_ACCOUNT_START_INDEX` to start a specific account range. Do not use one cursor file for concurrent jobs: each job needs its own allocated account range/cursor.

== Useful options

* `-Ddebug=on` — run a single virtual user.
* `-Denv=<name>` — override the configured environment label.
* `-DauthMode=none` — run without authentication (default).
* `-DauthMode=client-credentials` — attach a service access token to authenticated requests.
* `-DauthMode=password-grant` — temporary dedicated-test-user authentication for the local POC.
* `-DauthMode=token-pool` — pre-acquire one password-grant token per dedicated test account before the run.
